# Token ledger, quotes, payments and reconciliation

Use a **workspace wallet** and append-only `token_ledger_entries`, never `users.balance` as authority. One ledger row has workspace, wallet, signed available/reserved deltas, type/cause, related payment/job, idempotency key, actor and timestamp. Treat balance as two derived accounts: available and reserved. Example: purchase `(available +100,reserved 0)`; reserve 30 `(-30,+30)`; capture `(0,-30)` and cumulative spent +30; release `( +30,-30)`; refund a captured job `( +30,0)` with a linked refund cause. Keep purchased, promotional and spent totals by summing relevant types. A cached wallet projection may be updated in the same transaction and periodically checked against ledger sums.

## Price/quote contract

Versioned `PriceCatalog/PriceVersion` maps operation, Fast/Quality/Premium tier, duration, resolution, quantity, clipping length/count, transcription/script options, and billing rule to **customer tokens**. Provider/model routing and actual provider currency cost are separate admin-only records. Quote contains itemized child jobs, token total, max/partial-batch policy, expiry, and immutable price version IDs. Submission verifies quote hash and version; no retroactive repricing. Changes after a run starts apply only to newly quoted work, not existing child reservations. Do not show raw provider cost/margin to customer.

## Atomic paid-job lifecycle

In one serializable or row-locked Postgres transaction: authorize workspace spender → check active quote and available balance → enforce unique customer idempotency key/input hash → insert reserve ledger entry and Job/outbox → commit. A second tab/device cannot make available negative because wallet row lock/constraint serializes reservations. Success is terminal only after validated object/content persistence; then one capture entry closes reservation. Definitive failure/cancel creates one release. Transient retry retains the original reservation/price; extra cost beyond quoted ceiling requires a new explicit quote. Partial batch: one child reservation/capture/release per item; parent rollup never bills again.

Ambiguous provider timeout, lost callback, worker crash, and late success enter reconciliation; do not release a reserve before outcome is known and do not create a second provider execution. Duplicate callback/event and duplicate job-complete are no-ops via unique provider event IDs/job transition keys. If a late success arrives after a *definitive* release, quarantine artifact and investigate billing under the published policy; never silently take a second charge. Reconcile daily: wallet projections vs ledger, reservations vs nonterminal jobs, captures vs successful content, purchases vs settled payment events, provider bills vs executions. An admin-only adjustment requires actor, reason and audit event.

**Architectural recommendation:** target Xendit sandbox first for an Indonesia-based first paid release, with a `PaymentProvider` interface so Midtrans can be substituted if onboarding or commercial terms fail. This is a recommendation, not an established account or contract. Credit tokens only after verified server-to-server settled/paid state, matched amount/currency/order/workspace and unique event ID; browser return URL is informational. Payment webhooks are stored once, signature verified, processed transactionally, and periodically reconciled via provider status. Refunds and chargebacks create linked reversing ledger entries according to published policy. No payment was processed in Phase 0.

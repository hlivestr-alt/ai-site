# Private media storage design

**Recommendation:** private Cloudflare R2 bucket through a narrow S3-compatible storage interface; preserve ability to switch to AWS S3 or another S3-compatible provider if residency, contract, or operations require it. This is a design decision, not a configured bucket. Cloudflare documents S3-compatible [signed PUT/GET URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) and their bearer-token nature. Signed URL support does not itself enforce SaaS tenancy; our API must authorize before minting one.

Use opaque keys derived from IDs, e.g. `workspaces/<workspace-id>/assets/<asset-id>/versions/<version-id>/original`, `jobs/<job-id>/outputs/<asset-version-id>`, and `temp/<job-id>/<attempt>/<random-id>`. Never use customer filename in key or trust it as MIME. Asset metadata stores original display filename separately, `workspace_id`, purpose, product/version, source, rights/permissions, MIME declared and verified, byte count, dimensions/duration, SHA-256, storage class, retention/deletion state, and scan/probe result. Objects are not publicly enumerable; disable public bucket access. Avoid long-lived public URLs.

## Upload/download lifecycle

1. Authorize workspace Editor/Owner/Admin, intended product, size and type; create pending AssetVersion with fixed key and expected checksum. Return short-lived signed PUT, size/MIME constraints where storage supports them. For large footage use multipart upload protocol with server-owned upload ID and expiry.
2. Client uploads directly; API completes only after HEAD/probe, content sniffing, size/checksum, media decode and malware policy. Failed/incomplete upload stays pending and is swept after TTL. Generate thumbnail/review frames as separate versioned derived assets. Quotas and per-type limits are configurable: images, source footage and output video need distinct limits. Reject decompression bombs and unsupported codecs before worker claim.
3. On read, authorize current workspace membership and content/review/rights state against DB, then issue short-lived signed GET or stream via API. Signed URLs are bearer capabilities and may be reused until expiry; keep expiry short, avoid logging query strings, and use a download audit event. A removed member gets no *new* URL; already issued URLs expire quickly.
4. Worker claim provides only the source and output object grants for its lease/attempt. Worker validates checksum and writes to isolated temporary directory; upload goes to pending key. Server HEAD/probes and promotes DB state after completion. Expired lease cannot publish a content item even if an object upload finishes.

Retention: defaults and customer terms must be set before paid beta; keep historical product/workflow snapshots and ledger records even when original media is archived/deleted. Use soft delete and delayed object purge with legal/rights hold where required. Temporary processing objects and failed multipart uploads have short lifecycle rules; approved content has explicit retention/archiving policy. No cross-workspace deduplication of exposed keys or signed URLs. Deletion jobs must verify no content/workflow reference requires the object; recorded audit/ledger entries remain.

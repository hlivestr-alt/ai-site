# Customer tenancy, roles and launch-critical security

The current internal `AUTH_ENABLED=false` and one-click Outreach are not a customer architecture. For SaaS: managed customer authentication (email verification, recovery, invitation acceptance), server-side sessions, WorkspaceMember role checks on every API and media action. Owner controls billing and membership; Admin manages products/jobs/integrations according to explicit policy; Editor creates/spends/reviews within authorized limits; Viewer reads approved workspace data without spending or changing integrations. Exact role matrix must be locked in Phase 1 API tests.

Authorization query pattern: derive workspace from authenticated membership, require it as a query predicate or composite FK with object ID, and return 404/403 consistently for cross-tenant IDs. Never fetch `/products/<B-id>`, `/assets/<B-id>`, `/jobs/<B-id>`, content, ledger, or integration by global ID alone then rely on button visibility. Background callbacks/workers are authenticated principals scoped to one Job/lease rather than a user workspace session. Test ID substitution across all endpoints and signed media grants with Brand A/Brand B. Keep provider keys, payment secret and worker credentials in a secret manager; integrations store credential references encrypted and scoped to workspace. Rotate/revoke worker keys.

Media bucket is private; only API-minted short-lived signed URLs after membership/rights review. Upload confirmation validates actual bytes, not just supplied MIME. Payment webhook signatures and event uniqueness are mandatory; provider callback and worker lease tokens are checked and logged safely. Audit records actor/workspace/action/subject without storing raw secrets, media, message bodies, or payment card data. Separate customer/admin authorization and redact internal provider cost from customer API responses. Retain billing and deletion audit evidence in line with agreed terms.

**Top launch risks:** (1) public route to current no-login internal site; (2) cross-workspace object ID reads/writes; (3) leaked/public media URL; (4) duplicate or negative-balance token transactions; (5) payment webhook spoof/replay; (6) ambiguous provider cost/late success; (7) stale worker lease completion; (8) shared Clipper native data and product-specific prompt; (9) existing shared Outreach sender accidentally exposed; (10) insufficient support reconciliation/backup recovery. Address the first seven and support tools before paid beta; keep Outreach hidden until a separate customer authorization phase.

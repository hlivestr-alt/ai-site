# Local development and lifecycle

From `saas`, set `.env.local` from `.env.example`, including `DATABASE_URL`, `TEST_DATABASE_URL`, separate `OBJECT_STORAGE_BUCKET` and `TEST_OBJECT_STORAGE_BUCKET`, loopback `OBJECT_STORAGE_ENDPOINT=http://127.0.0.1:9000`, region and local credentials. Run `docker compose --env-file .env.local up -d`, `npm install`, `npm run db:migrate`, `npm run storage:init`, then `npm run dev`. `npm run db:status` shows applied migrations. Compose restarts preserve Postgres and storage volumes. Run storage initialization again only to ensure buckets exist; it does not erase objects.

Test setup applies migrations to the isolated test database and ensures both buckets exist. Test media are written only to the test bucket. To reset local data intentionally, stop the SaaS app and Compose, then remove the **SaaS-specific** volumes and recreate/migrate/initialize together. Do not reset only Postgres or only storage: that would leave dangling references or untracked objects. The cleanup script does not reset either service.

`npm run storage:cleanup` is a dry run listing up to 100 pending AssetVersions older than `PENDING_UPLOAD_RETENTION_HOURS` (24 by default) in the dev DB. `npm run storage:cleanup -- --apply` marks those versions `FAILED`, marks new assets failed when they have no current version, and deletes only their staging upload keys. `npm run storage:cleanup -- --test` targets the test DB/bucket. Re-run in batches if needed. Finalized originals, thumbnails and historical versions are retained. A delete error leaves a marked failed version for operator follow-up; no automatic scheduler is installed.

If the provider is unavailable, upload URL creation or finalize fails visibly and a pending upload may be retried. A copied final object without a completed DB update can be finalized on retry. The system does not purge historical objects on Product or Asset archive. Operators should monitor storage availability, failed assets, orphaned staging keys and volume capacity before production use.

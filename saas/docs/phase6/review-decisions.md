# Review decisions

`review_decisions` is append-only. It stores workspace/item/version/reviewer, APPROVE or REJECT, optional reason, request key/hash, review revision and time. API decisions and item status/revision changes commit with the audit event in one transaction under the item row lock. History uses display names and escaped React text. Reject never deletes media. An authorized reviewer may later approve a rejected version or reject an approved version; history keeps every accepted decision.

Approve has no rejection category/text. Reject requires a permitted category and accepts optional readable text of at most 1,000 characters. Generic clips permit `BAD_CLIP_SELECTION`, `CAPTION_ISSUE`, `QUALITY_ISSUE`, `OTHER`. Product-backed items additionally permit `LOGO_WRONG`, `PACKAGING_TEXT_WRONG`, `PRODUCT_SHAPE_WRONG`, `CAP_PUMP_WRONG`, `COLOR_MATERIAL_WRONG`, `APPLICATION_METHOD_WRONG`. The database bounds categories/text; server validation selects the allowed category set for the item.

Requests contain `versionId`, `expectedRevision`, `decision`, and a bounded 8–160-character `requestKey`, plus rejection fields when applicable. The request hash covers normalized decision/version/revision/reason. Identical retries with the same key return the prior decision without another history row or audit. Reusing the key with different payload returns 409. The browser retains the same key for a retry of that same decision and creates a new key when version/revision/decision or rejection fields change.

Concurrent identical approvals using one key return two successful responses and one decision. Different concurrent requests with the same expected revision serialize: one succeeds and one returns 409, including Approve versus Reject. The losing reviewer must refresh before submitting a new decision. Historical idempotent retries can return their previous decision ID and today's status, but cannot reapply that old decision. Archived items reject new reviews.

Current status is materialized on ContentItem. A current pointer change resets Pending Review and increments the revision. `isContentApproved(workspaceId, contentId, versionId)` requires the same workspace, current version, APPROVED status and matching current-revision approval history. It returns false for stale versions, Pending, Rejected and Archived. It is an internal server helper; callers must authorize their workspace before use. Audit types are `CONTENT_PUBLISHED`, `CONTENT_APPROVED`, `CONTENT_REJECTED`, `CONTENT_ARCHIVED`, `CONTENT_RELATION_CREATED`, storing safe IDs/categories without signed URLs or free-text reasons.

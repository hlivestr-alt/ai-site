# Logging and alerts

Application/dispatcher events use JSON lines on stderr: UTC time, service, event, stable safe code, and relevant request/workspace/Job/Run/instance identifiers. `X-Request-Id` is validated or generated by the request proxy and reaches response errors, audit entries and Job/Workflow events. Server errors return a safe message/code and a support reference; raw SQL/provider/storage errors do not enter API responses.

Do not log passwords, bearer/callback/API tokens, full signed URLs, raw provider payloads, user prompts, SMTP bodies, environment values or filesystem paths. CLI machine-readable result JSON stays on stdout. Enrollment credentials are one-time operator output; capture them directly into the private secret store rather than general logs.

The restricted status/metrics payload exposes infrastructure unavailability, dispatcher freshness, worker offline/disk pressure, billing mismatches, recent reconciliation issues, uncertain provider submissions, publication/poster/mail backlog, storage quota approaching 90%, and missing/stale backups. Billing examples and issue examples are bounded; investigate exact IDs through support. Waiting-for-funds/review is advisory, never an automatic failure rule.

Use `operations.ts audit` for the daily read-only accounting, Workflow, Job and Content audit. Schedule it through the deployment supervisor or monitoring system and alert on new/actionable findings. No external notification provider is installed and no user message/email is sent by these audit tools.

Protect log access and rotate by age/size (for example daily plus a fixed size cap, 14-day operational retention). Keep financial/audit retention according to the operator's policy separately; rotation must not delete database history. Investigate incident references rather than requesting customer credentials.

# Storage operations

All sealed objects live under workspace-scoped identities. Public bucket access, static application media serving and broad listing are inappropriate for deployment. Product media GET URLs last 60 seconds; AI/Clipper/Content/source/worker source GET URLs last 300 seconds. Product and worker output PUT URLs last 300 seconds; source upload/multipart signing uses 900 seconds. Authorization precedes signing. A valid bearer URL expires; possession during its lifetime grants access to that one object.

Usage is derived from database object references, deduplicated by workspace/key: original Product versions, thumbnails, uploaded/verified/archived sources, READY Job artifacts, and READY posters. Immutable/historical objects remain counted. Content is a reference to a Job artifact and adds no second copy. Reported known bytes are separate from pending/provisional quota allocations. Provider bucket inventory/version overhead and unreferenced objects are outside this application approximation; monitor vendor storage totals as well.

Run `npm run storage:audit -- <workspaceId> [limit]`. Default 100, maximum 1000 objects per explicit workspace/category. It checks known sealed references for presence/size/scope, known old pending/failed staging and unsealed copies, and exact failed-poster attempt keys. Multipart listing is limited to that workspace's source staging prefix and one bounded page; missing listing support is explicit/partial. Results contain IDs/categories/statuses, never keys or signed URLs. The default is report-only and deletes nothing. Check historical references and backing artifacts before considering any retention change.

Recommended vendor lifecycle: expire `pending/` objects after at least 24 hours; abort incomplete multipart uploads after a reviewed period (for example 7 days); protect `workspaces/` sealed content and backup retention. Review real endpoint/permission/CORS behavior before applying policy. Enable versioning/encryption and offsite backup retention according to the chosen provider and cost policy. No production lifecycle policy is applied automatically.

Existing `storage:cleanup` is a bounded dry run and permits --apply only in local/test mode; it addresses old asset staging objects only. Staging/production cleanup, source multipart cleanup and retained failed/unused artifacts require investigation, an explicit audited operator procedure and provenance. Do not treat a bucket listing or age alone as permission to delete immutable media.

Production multipart/large-object acceptance is still required: part retry/resume, completion, ETag/size checks, >5 GiB multipart copy, interrupted sealing, range/media reads, browser CORS and expiration on the actual vendor. Source sealing now performs byte/copy work outside DB transactions and rechecks membership/state/quota before committing READY eligibility. Start beta with a deliberately smaller source limit until these vendor/throughput checks pass. Local S3 fixtures do not certify large production objects.

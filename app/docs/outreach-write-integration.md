# Outreach campaign write boundary (Phase 3)

The existing backend at `127.0.0.1:4000` already exposes the business operations needed for campaigns. `POST /api/v1/outreach/campaigns` allocates a campaign name and saves a DRAFT. `POST /:id/discovery-runs` filters the local creator database, applies contact/cooldown/reservation rules, and persists a PREVIEW_READY selection. `GET /:id/recipients` reads recipient preview records without the expiration side effect of `GET /:id` or `GET /:id/preview`. `POST /:id/freeze` takes the current campaign version, rechecks eligibility, creates reservations, renders immutable recipient messages, and moves to FROZEN. `POST /:id/send` with current version queues the frozen recipients using native durable outbox semantics; when called from PREVIEW_READY it can freeze and queue in one action. `POST /:id/pause` and `/resume` use the native campaign state machine. The outbound worker alone sends and handles pacing, provider limits, retry, and DELIVERY_UNKNOWN.

AI Site's `src/lib/integrations/outreach/write.ts` allows only create, discover, and freeze POST paths. It validates native fields and maps recipient preview to relevant display fields. Server routes require JSON and reject a foreign browser Origin. The new `/outreach/new` flow explicitly separates draft creation, native preview, native freeze, and final confirmation. The native backend ignores client-supplied campaign names, so the form explains automatic naming. The UI exposes supported keyword, follower, GMV, unit, view, live-viewer, and engagement filters; ranking and cooldown are native fields. It does not invent additional selection rules.

`Confirm & Queue` is intentionally disabled. Production Compose sets outbound mode to live, and no safe non-production end-to-end send validation path was identified. We did not test create, discovery, freeze, send, pause, or resume against the live backend. Pause/resume are supported by native HTTP but stay in the native operator app for this phase; resume can release real sends. The platform contains no `/send` route and its client allowlist rejects that path. No second sender, direct SQL writer, queue algorithm, or provider client was added.

The existing read-only PostgreSQL overview remains the source for campaign and sending counts because native campaign list/detail GETs can expire campaigns as a side effect. The wizard refreshes that overview for campaign version after native writes. Preview records come from the native read-only recipients endpoint. `OUTREACH_API_URL` is server-only, defaults to local port 4000, and never reaches the browser. The app has no independent operator authentication; local use and a reviewed access-control plan are required before any queue action is enabled.

Settings reads `GET /api/v1/system/status` through a sanitizing server adapter for the native outbound worker and sender capability. Its implementation is read-only in the deployed `APP_MODE=read_only`; it queries infrastructure and heartbeat state. The platform exposes only availability and worker state, not raw integration details.
